## Архитектура проекта

Весь проект развернут в единой сети Docker Compose и состоит из следующих контейнеров:

1. **db** - база данных PostgreSQL.
2. **redis** - брокер сообщений для Celery.
3. **main_api** - основное FastAPI приложение.
4. **parser_api** - отдельный микросервис для синхронного парсинга по HTTP.
5. **celery_worker** - фоновый обработчик задач парсинга.
6. **flower** - веб-интерфейс для мониторинга задач Celery.

Для обеспечения правильного порядка запуска я добавил `healthcheck` для базы данных и Redis. Это гарантирует, что API и Celery начнут работу только после полной готовности БД.

## Написание Dockerfile

Для всех Python-сервисов используется единый `Dockerfile`, написанный с учетом Best Practices:

```dockerfile
# Указываем базовый образ
FROM python:3.11-slim

# Настраиваем переменные окружения
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

# Устанавливаем системные зависимости и сразу очищаем кеш
RUN apt-get update && apt-get install -y --no-install-recommends \
    libpq-dev gcc \
    && rm -rf /var/lib/apt/lists/*

# Устанавливаем Python зависимости
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

# Создаем пользователя без прав root
RUN useradd -m -U appuser && chown -R appuser:appuser /app
USER appuser

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

## Два подхода к парсингу

В рамках лабораторной работы нужно было интегрировать парсер веб-страниц, написанный ранее. Я реализовал два варианта его вызова: через микросервис и через очередь.

### 1. HTTP-взаимодействие микросервисов

Был создан отдельный контейнер `parser_api`, который слушает порт 8001 внутри докер-сети. Основное приложение обращается к нему через эндпоинт `/parse/http`.

```python
@router.post("/http")
async def parse_via_http(request: ParseRequest):
    async with httpx.AsyncClient() as client:
        response = await client.post(PARSER_API_URL, json={"url": request.url}, timeout=15.0)
        return response.json()
```

В этом сценарии клиент делает запрос к основному API и ждет, пока микросервис скачает страницу, распарсит ее и сохранит в БД. Если сайт отвечает медленно, клиент будет долго ждать ответа.

### 2. Очередь задач на базе Celery и Redis

Для долгих задач лучше подходит асинхронный подход с брокером сообщений. Я настроил Celery, который использует Redis в качестве брокера. 

Эндпоинт `/parse/celery` принимает запрос и мгновенно ставит задачу в очередь:

```python
@router.post("/celery")
async def parse_via_celery(request: ParseRequest):
    task = parse_url_task.delay(request.url)
    return {"message": "Parsing task submitted", "task_id": task.id}
```

Клиент сразу получает `task_id` и не заблокирован ожиданием. Парсинг происходит в фоновом контейнере `celery_worker`. Позже результат можно получить через отдельный GET эндпоинт:

```python
@router.get("/celery/{task_id}")
async def get_task_status(task_id: str):
    task_result = AsyncResult(task_id, app=celery_app)
    # Возвращаем статус или готовый результат
    ...
```

Для визуального контроля за очередями задач поднят контейнер с Flower.

## Сравнение подходов

| Критерий | Вызов по HTTP | Очередь Celery |
| :--- | :--- | :--- |
| **Время ответа клиенту** | Долгое - ждет завершения парсинга | Мгновенное - задача уходит в фон |
| **Сложность инфраструктуры** | Простая - только два API сервиса | Сложная - нужен Redis, Worker и Flower |
| **Устойчивость к сбоям** | Низкая - при ошибке сети запрос падает | Высокая - задачу можно перезапустить |
| **Идеальный сценарий** | Быстрые задачи | Парсинг множества страниц, рассылки |

## Вывод

Я на практике изучил упаковку проекта в Docker. Использование контейнеров сильно упрощает запуск приложения: одной командой `docker-compose up` поднимается сразу 6 связанных сервисов. 

Сравнение двух подходов показало, что для задач вроде парсинга лучше использовать очередь Celery. Это усложняет архитектуру, но делает приложение более отзывчивым для пользователя и надежным под нагрузкой.
